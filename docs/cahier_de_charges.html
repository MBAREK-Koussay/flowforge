1. Contexte & Objectifs

FlowForge est une plateforme SaaS de type ERP (Enterprise Resource Planning) orientée automatisation de processus métier. La solution permet aux entreprises de gérer leurs données opérationnelles (clients, produits, stocks, achats, factures) puis de modéliser, exécuter et surveiller des processus métier automatisés à travers un constructeur de workflow visuel.

1.1 Problématique

Les processus métier répétitifs (approbation d'une demande d'achat, relance de facture, alerte de stock) sont souvent gérés manuellement (e-mails, tableurs), ce qui engendre : lenteurs, pertes de traçabilité, erreurs humaines et absence de contrôle.

1.2 Objectifs

  • Centraliser la gestion des données ERP au sein d'une application unique.
  • Permettre la création visuelle de processus par des utilisateurs non-techniques (drag & drop).
  • Exécuter automatiquement les processus déclenchés par des événements métier.
  • Traçabilité complète : historique d'exécution, audits, statuts en temps réel.
  • Assister la conception de workflow grâce à un générateur IA.

1.3 Public cible

Responsables opérationnels, gestionnaires, équipes financières et employés souhaitant automatiser des tâches quotidiennes sans écrire de code.

3. Exigences Fonctionnelles

3.1 Module 1 — Simulation Mini-ERP

Gestion des utilisateurs

  • Authentification (enregistrement, connexion, déconnexion), tokens Sanctum.
  • Quatre rôles : Admin, Manager, Finance, Employee.
  • Assignation de roles et permissions (RBAC).

Clients

CRUD (création, lecture, recherche, filtrage, mise à jour, suppression), statut actif/inactif.

Produits & Stock

  • CRUD produits (nom, SKU unique, prix, quantité, seuil minimum).
  • Mouvements de stock avec historique et référence morph.
  • Détection automatique des stocks faibles.

Demandes d'achat

Créées par un employé ; statuts pending / approved / rejected ; montant, description.

Factures

Montant, échéance, statut pending / paid / overdue ; marquage payé ; détection auto des retards (scheduler).

Données de démonstration : 50 clients, 100 produits, 20 employés, 100 factures, 50 demandes d'achat générées par factory/seeder (données présentes après installation).

3.2 Module 2 — Gestion des Workflows

Un workflow associe des entités : nœuds (positionnés) et connexions. Entités versionnées et dotées de statut (draft / active / paused / archived).

3.3 Module 3 — Constructeur Visuel

Interface React Flow : glisser-déposer de nœuds, création de connexions, suppression, configuration via panneau latéral, sauvegarde et chargement. Types de nœuds :

  • Déclencheur (trigger) : facture créée, demande d'achat créée, stock mis à jour.
  • Action : envoyer un e-mail, notification, mettre à jour une entité, générer PDF.
  • Condition : ex. si invoice.amount > 5000.
  • Approbation : approbation manager / finance.
  • Délai : attendre X jours.
  • Webhook : appel HTTP externe.

3.4 Module 4 — Moteur d'Exécution

Démarrage automatique sur événement métier, exécution séquentielle des nœuds, évaluation des conditions, gestion des erreurs et sauvegarde de l'historique. Composants : WorkflowRunner, NodeExecutor, ConditionEvaluator, ActionExecutor. Appui aux jobs & files d'attente.

3.5 Module 5 — Approbations & Notifications

Demande d'approbation : approuver / rejeter / commenter ; historique ; notifications e-mail et internes.

3.6 Module 6 — Tableau de Bord

KPIs : workflows totaux/cours/complétés/échoués, temps moyen d'exécution, approbations en attente. Graphiques : performance, workflows les plus utilisés, latences processus.

3.7 Module 7 — Avancé

Modèles (approbation d'achat, relance invite, alerte stock, onboarding), versionnage des workflows, journaux d'audit (qui/quoi/quand), suivi temps réel des nœuds (running / completed / failed) via Reverb.

3.8 Module 8 — IA

Générateur de workflow : "crée un workflow qui approuve les factures au-dessus de 10 000 TND" → génération JSON (déclencheur + condition + approbation) importable dans le constructeur.

4.1 Vue d'ensemble des couches

4.2 Styles d'architecture

  • Monolithe modulaire : le code est groupé par domaine (Domain/Customer, Domain/Workflow…), favorisant la maintenance et un découpage ultérieur en microservices.
  • Principes SOLID : responsabilité unique (services), inversion de dépendance (IPorts via interfaces de repository).
  • Couplage faible ERP ↔ Moteur : les événements métier (ex. PurchaseRequestCreated) déclenchent des listeners qui résolut les workflows actifs puis jettent un job.
  • Exécution déterministe & reparable : chaque nœud écrit une ligne workflow_logs, permettant de reprendre un run échoué.
  • Enumérations pour les statuts (pas de chaînes magiques).

7. Moteur d'Exécution de Workflow

7.1 Cycle de vie d'un workflow

Pour l'exemple cible "Approbation d'achat" :

Demande d'achat créée  ↓ [Événement PurchaseRequestCreated]
   → File d'attente (job RunWorkflow)
   → WorkflowRunner : récupère le graphe, initialise un run
       → NodeExecutor : exécute Déclencheur
       → ConditionEvaluator : amount > 5000 ?
           ✓ → Approbation Manager
                ✓ → Approbation Finance
                     ✓ → Notification (e-mail)
                          ✓ → Action: mettre à jour le statut
       → Logs de route + run finish

7.2 Composants clés

  • WorkflowRunner : orchestration d'un run.
  • NodeExecutor : dispatch par type de nœud.
  • ConditionEvaluator : évalue les conditions (opérateurs, types).
  • ActionExecutor : exécute les actions (mail, notification, update record, webhook, délai).
  • Approbation : affirmation d'un run (awaiting_approval), reprise après décision.
